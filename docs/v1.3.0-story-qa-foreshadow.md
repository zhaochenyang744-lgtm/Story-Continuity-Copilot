# Bounded Q&A and foreshadow records

## Product position

Bounded Q&A and foreshadow scanning are secondary tools on the existing Writing surface. They do not replace the manuscript editor, add a chat destination, or create a parallel source of truth.

The author remains responsible for every durable foreshadow record. AI output is either a read-only answer or a reviewable candidate and never changes the draft, committed sources, Story Memory, Author Context, character aliases, or another author record by itself.

## Bounded Q&A

One request contains one question and at least one selected evidence layer:

- `confirmed` contains only records from the bound Story Memory version.
- `written` contains only bound current-draft claims and resolvable SourceSpans.
- `planned` contains only records from the bound Author Context snapshot.

The result status is `answered`, `partial`, `insufficient`, or `conflicting`. Every non-insufficient finding belongs to exactly one layer and carries one or more resolvable citations from that same layer. A conflicting answer must include both supporting and contradicting findings backed by different evidence. An insufficient answer uses deterministic product copy and discards unsupported Provider prose.

## Author foreshadow records

Each record contains a title, description, status, optimistic version, and optional planted and resolved chapter or SourceSpan associations. Supported statuses are `planned`, `planted`, `developing`, `resolved`, and `abandoned`.

Create, update, and archive operations require idempotency keys. Updates and archives compare the submitted record version, while creates compare the project foreshadow version. Normalized active titles are unique within one project. Every accepted mutation stores an immutable snapshot event and advances the project foreshadow version. Cross-account and cross-project identifiers resolve as not found.

## AI foreshadow candidates

`foreshadow_scan` uses the shared analysis Run lifecycle. Its bounded input includes the saved draft identity, current source revision, Story Memory version, Author Context snapshot, current foreshadow snapshot, selected draft claims, and selected SourceSpans. Story Memory and Author Context may establish binding freshness but cannot serve as written proof for a candidate.

Every candidate contains a title, description, suggested status, and at least one written citation labelled as planted, developing, or resolved. Empty output becomes a deterministic insufficient result. Duplicate candidates, unresolved citations, invalid JSON, timeout, cancellation, and schema mismatch fail closed without partial candidate storage.

Candidates are stored separately from author records. The author may:

- accept the exact candidate;
- edit its title, description, status, or source associations and then accept it;
- reject it without creating a record.

The accepted record and candidate decision are written in one transaction. A decision never writes the manuscript, sources, Story Memory, Author Context, aliases, or unrelated author data. Multiple candidates from one Run can be decided in sequence; another author-record mutation makes the remaining candidates stale.

## Run bindings and recovery

Both analysis types record the exact draft revision, source revision, Story Memory version, Author Context version and digest, foreshadow version and digest, retrieval method, model label, schema label, and immutable input digest. Results become stale when a relevant binding changes. Retry creates a new Run from the same still-current immutable input; stale input must be regenerated from current state.

Run lists retain status, cancellation, retry lineage, terminal errors, and prior results. Late Provider responses after cancellation are discarded. No intermediate reasoning or partial result is exposed.

## Interface and evidence

Desktop Writing presents these tools beneath the established brief and alignment area. Author records, AI candidates, and written evidence use explicit labels and separate visual groups. Citation links route only to existing project pages and visible record anchors.

At 390 px the same section is browse-only. Existing records, candidates, decisions, answers, bindings, and evidence links remain visible; create, edit, archive, ask, scan, candidate decision, retry, and cancellation controls are absent. The page must remain keyboard-readable and free of horizontal overflow.
