# 当前契约比较集：独立准备审查

2026-09-26。本文件仅为设计与验收建议；新比较集尚未由本审查建立、冻结或执行。本次只读核对最终真实评测验收报告、V8 独立诊断及当前 continuity 契约/检索源码，不修改产品、旧评测或 protected held-out。执行顺序沿用主控：先修 G02，再整理当前契约比较材料。

建议采用 **24 个全新固定开发回归案例：8 冲突、8 无冲突、8 证据不足**，组织为 8 组相近的三联例，至少来自 4 个新的合成作品。另选三类各 1 个代表，首轮之外各重复 2 次，共 6 次稳定性运行；重复不能增加独立案例数。该规模用于发现明确回归和做配对比较，不足以得出模型总体优劣或泛化准确率。材料经开发/审阅后属于已暴露集，不称未见集。

| 最低组成 | 必須预先写明的语义条件 |
|---|---|
| 8 个冲突 | 8 个当前类别各有 1 个明确实例；其中至少 2 个真实静态规则场景，其余覆盖有明确同一时间/范围的动态状态、知情与事件。类别按核心矛盾标注，不能用规则词出现与否机械分类 |
| 8 个无冲突正控制 | 每个冲突配一个接近但兼容的场景，保持相近实体、来源数量、文本长度和干扰程度；至少覆盖明确后续转移/后知、跨日、回忆/谎言、规则条件不成立，防止一律降级或一律输出空数组 |
| 8 个证据不足 | 在相同主题中明确缺少判定所需的结论、身份、授权或连接事件，标出缺失的逻辑环节；至少 4 个由两条及以上材料共同呈现边界。不能仅因草稿增加新情节，就把“历史正文未出现”当作证据不足 |
| 多证据和干扰 | 至少 4 个冲突需要 2 条直接证据，逐条说明为什么单条不够；三联例均保留同名/同主题干扰，不靠去掉难例或给冲突单独加检索便利来提高分数 |

三联例可做受控事实变化，但应重新设计故事事实、证据结构和人工理由，明确同组依赖；不能把旧 V8 的 fixture_anchor 改成 rule、换人名或搬旧答案称为新集。三联例是 24 个输入、8 组相关情景，不是 24 个统计独立故事。

## 标签与当前契约一致

1. **冲突的严格命中**：目标 claim 的 `status=conflict` 且 `nature=confirmed_conflict`，类别正确，引用包含人工判定的完整直接证据，解释的主体/范围/时间关系真实成立。`possible_conflict`、兼容 `state_change` 或保守降级不能充当确定冲突命中；额外无根据 Issue 同样使该案例严格失败。
2. **无冲突**：语义确实兼容，预声明允许省略 Issue；明确转变案例还可允许有充分证据的 `state_change`。当前底层 status/classification 可能仍写 conflict，评分必须查看 nature 和内容，不能直接复用旧三分类投影。不得把没有完成的请求、超时或无效 JSON 的空结果算无冲突。
3. **证据不足**：目标 `status` 和 `nature` 都为 `insufficient_evidence`，引用为对应 context/insufficient，evidence_chain 标 missing_link，并准确解释缺少什么；无 actions 或 Memory 改写。为了强凑三类，把兼容的新情节标成不足、或把 possible_conflict 静默计作不足，均不接受。

静态规则必须确实是故事中稳定适用的约束，SourceSpan 有原文，作者确认 Memory 以 `static_canon / rule` 保存规则内容与适用范围、绑定原来源。动态保管、知情、结果等使用真实相应 Memory 类型/谓词；不能为过校验伪装成 rule。动态确定冲突的同一时间锚点必须存在于该 claim 和自身证据，不借邻句、章节顺序或“当前场景”。before/after 的事件排序不是自动成立的 explicit_overlap；若自然事实成立但现有 matcher 无法表达，保留为契约能力缺口，不能拼接虚假时间短语让它通过。

每例至少记录 `expected_class`、允许的 nature/temporal relation、目标 claim 文本及绑定、类别及简短理由、必需证据集合（可有预声明的等价充分集合）、逐证据事实/缺失环节、禁止的过度结论和三联组 ID。先独立人工复核标签，再冻结；以最小合法响应做离线契约可表达性检查，不能用“validator 接受”代替语义审阅。

## 输入完整性是比较前提

当前链路为 DB top5，再由 engine 二次排序仅发 3 条，每条最多 500 字；Memory 相关度有 10 倍权重（`backend/app/v2_database.py:3273-3279`；`backend/app/engine.py:21-22,218-231`）。因此建议比较集每例核心论证不超过 3 个来源，但保留真实干扰；超出容量的压力情形另列检索回归，不混成纯模型胜负。

用真实产品 API、隔离 fixture、fake Provider 捕获**实际完整业务请求**，逐例离线核查：

- 章节正文、SourceSpan、摘要、revision 一致；Memory 完整字段、版本/确认状态/来源正确。深处事实或缺失事实在完整父章节与片段上必须一致。
- 冻结目标正文实际进入正确 claim；比较时按 claim_id/ordinal 匹配，不只取首个 Issue。至少一例含相邻非目标句，用于发现锚点或评分串句。
- 同时保存 DB top5、模型最终 SourceSpan ID、实际 excerpt 和截断位置；所有必要事实及其限定词必须实际在请求中。ID 被选入但关键句被截掉不算证据齐全。
- 不足类“缺少事实”应在整个冻结作品/Memory 中审阅确认，而非把本来存在的事实靠检索遗漏隐藏；把检索失败误当合理不足会污染金标准。

若某例缺证据或不符合契约，明确记录为检索/材料/契约失败并暂停其纯模型归因；不悄悄补入 oracle 证据、改标签或移出产品总分母。若需要一套直接提供完整证据的推理对照，另记独立诊断输入身份，不能与生产检索输入混成同一成绩。

## 首答、产品和比较验收

分别保留首个实际响应、所有修复响应、最终产品输出和归一化记录；逐次请求绑定 hash。严格分开报告：

- **语义三类混淆矩阵**与 **严格案例通过数**：严格通过还要求性质、类别、时间/规则依据、完整证据和自身引用均正确；列整数分子分母，不能只报宏 F1。
- 确定冲突 precision/recall、兼容正控制误报数、不足类召回；possible_conflict、state_change、修复、降级和失败各自计数。关键兼容控制不能出现无根据确定冲突；这是本小样本的阻断信号，不是零错误保证。
- 检索 top5 命中、最终 prompt 完整证据率、片段事实覆盖、逐项引文支持、跨章节/跨项目归属分别评分。`supported`、结构合法和引用可解析都不能替代语义支持。
- 全部 24 例始终进入产品回归账本；模型条件成绩另明示哪些实际输入满足完整可比较条件及其数量，不能静默剔除失败再报高分。若 24 例未全满足输入前提，暂不宣称完成公平模型比较。
- 3 组重复分别评语义决策、性质/类别、语义证据集合；自由解释文字逐字一致另列，不作为主要稳定性要求；错误重复不称质量稳定。

比较模型/提示词时，预先固定唯一区别、同一案例、完整业务输入、代码 hash、schema、模型请求与响应标识及参数。不要同时改变 fixture、检索和模型再把分差归于模型。首轮记录能力基线与每个失败；后续版本采用同输入配对错误清单，不用 24 例的偶然微小分差宣布谁更好。质量阈值和关键控制必须在看到真实响应前由计划固定，不能照结果调低。

## 建集交付的最低验收清单

1. 新版本路径与 create-only run 身份；24 例分布、8 组三联关系、4 个作品、人工标签/证据理由清单齐全。
2. 24 例离线材料一致性、实际请求捕获、目标绑定和合法契约可表达性均通过；必要证据实际到达率 24/24，缺失事实未被其它来源偷偷补齐。
3. 评分器负控制能识别：possible 当 confirmed、state_change 被旧 status 误算冲突、引用 ID 齐全但各项错配、句尾截断、跨章引用、失败空输出和首答/最终混算。
4. 冻结 corpus/cases/rubric/runner/score 与实际产品/seed 依赖、全请求 hash；保存首答、后续响应、最终结果和准确的调用/usage；旧 V1/V2/V3、V8 结果和首次失败不改。

以上只是待实施和验收规范。没有创建案例、运行离线/真实评测、访问业务数据库、读取密钥或调用 Provider。
