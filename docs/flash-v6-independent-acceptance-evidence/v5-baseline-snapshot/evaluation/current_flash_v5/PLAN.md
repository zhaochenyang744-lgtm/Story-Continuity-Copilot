# Current Flash V5 preparation and bounded live matrix

## Fixed matrix and identity

This is an exposed development evaluation: 24 accepted `current_contract_compare_v3` cases (eight conflict, eight compatible, eight insufficient) plus six `current_flash_v4` G02 bodies, one logical input each. The first four G02 drafts are byte-identical to V2; the time and dialogue bodies are byte-identical to V4. Current quote-aware splitting produces **two complete attributed dialogue claims**, unlike the old V4 captured request's three pieces and closing-quote-only tail. V5 captures its own current API request and never substitutes a V4 request.

There are no stability or exploratory calls. The two supported `state_change` outcomes are accepted answer forms within the 24 cases, not extra samples. Each comparison input is one claim and one batch. The hard generation POST ceiling is `24 × 2 contract evaluations × 2 transport attempts + 6 × 1 × 2 = 108`; one `/models` GET is the only model preflight. The actual product keeps `deepseek-flash`, `https://api.deepseek.com`, JSON-object response mode, disabled thinking, temperature 0, its frozen max tokens, 30-second timeout, and one timeout retry. A quality or category failure does not cause a new logical run.

## Durable evidence before network

The run ID and isolated workspace are reserved create-only before source loading, fixture creation, API use, or Provider dispatch. Every output uses create-only writes. For each case, the saved draft, source revision, Memory version, full synthetic SourceSpan text, parent chapter identity, isolated database Memory rows, and same-run business request are written before any Provider POST. Every evaluation (first or contract repair) has its own request snapshot. Every transport attempt has an `attempt-start` file written and fsynced immediately before `client.post`; its finish record stores status, usage classification, response metadata and **message business content only**. It never stores authorization headers, keys, hidden `reasoning_content`, or a malformed envelope body. A bad model JSON content string remains available in the finish record even when parsing fails. Parsed business JSON, repair answers, and final persisted API product are separate files.

An isolated `attempt-start` proves a local dispatch was prepared, not that the remote service received it. Summary fields separate start records, finished transport attempts, observed HTTP responses, and unfinished unknowns. Usage is `complete`, `missing`, `partial`, or `unknown`; known token fields have a partial sum, while totals are null unless every attempt has complete usage. A timeout or missing usage is never counted as zero. `/models` start and finish are likewise separate. Reusing an ID fails before fixture/API; no restart automatically re-dispatches a case whose attempt may have been sent.

Service-stop preserves the earlier rule: HTTP 400/401/403/404 stops immediately; two consecutive logical cases containing any transport/service error stop even if a retry subsequently succeeded. A parseable but malformed business JSON is saved and scored `unscorable` or `score_error`; if it causes a product API exception, absence of a final product is recorded and the next fixed case proceeds without retry. Input binding or fixture failure stops the run with a first-failure file.

## Input and scoring scope

The 24 comparison cases load V2 synthetic corpora through a new isolated `Stage13Settings.for_test()` app; the same-run request is compared to frozen V2 capture with only its ephemeral claim ID normalized. Minimum Evidence must be selected. The six G02 cases save the draft anew and check retrieved claim ranges, chapter/span ID and revision, and selected Memory against the **same isolated database**. The 1980-character repeated body must yield 180 available claims, 8 selected and 172 unselected; duplicate wording keeps two distinct claim IDs. The dialogue must yield two complete quoted claims. The selected G02 SourceSpan text and controlled Memory are separately checked; a Memory's source can legitimately be outside the selected source subset.

The G02 teaching seed has empty parent-chapter bodies and populated synthetic SourceSpans. V5 checks the parent chapter ID/title/revision and SourceSpan text, but it **does not** establish a full-chapter or long-manuscript source chain. It does not fabricate or backfill chapter prose.

Continuity first raw, each repair raw, and final product are scored in distinct layers by the accepted V3 scorer. Failed/timeout empty Issues are terminal, `possible_conflict` is not confirmed, and conservative product normalization is not first-answer correctness. G02 automated checks cover citation ID binding for each raw/final item and summary; whether the wording is semantically supported by its own citation remains manual. `state_change` and the companion's declared category variant retain their V3 rules, with the latter pending human adjudication. None of these machine results is a blind-set or generalization accuracy claim.

## Execution boundary

Preparation uses only a stub and isolated SQLite under the ignored `artifacts/current_flash_v5` path. This file, cases, runner, scorer, journal, fixture/product dependencies, parameters and final 30-case preparation capture are frozen before live dispatch. The named existing process environment variable `CONTINUITY_API_KEY` is consumed only by the live command; no `.env` or credential store is read or written. The controller first reviews this frozen preparation and then sends the live execution instruction. No commit, push, merge, deploy, real author workspace, SMTP, or UI rerun belongs to V5.
