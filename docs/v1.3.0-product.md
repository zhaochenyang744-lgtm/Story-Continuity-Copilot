# Story Continuity Copilot v1.3.0 product contract

This is the single product entry for the local v1.3.0 release candidate. The active online product remains v1.2.0.

## Product problem

Long-form fiction authors need help comparing future intent, written prose, and confirmed canon without allowing an assistant to blur those categories or silently change the story. v1.3.0 gives the author one controlled path from planning to writing and from new prose to reviewed Story Memory.

The product is a continuity copilot, not a chat assistant, prose generator, or automatic editor. AI is used only where comparing bounded story state creates a decision the author can inspect.

## Complete author path

1. Open Home or Works, select a project, and review its overview.
2. Record future intent in story, character, and world planning.
3. Open Writing and generate a bounded chapter brief before drafting when useful.
4. Write and save the draft. Unsaved text remains local to the editor and is never analysed as a saved revision.
5. Compare the saved draft with selected plans and run continuity review against written sources and confirmed Memory.
6. Select open findings from the current check and generate bounded revision suggestions when useful; accept, edit and accept, or reject each suggestion.
7. Use accepted suggestions as persistent author tasks, return to the same draft, edit prose manually, and explicitly save it. Task completion never resolves an Issue or starts another check.
8. Explicitly rerun continuity review, inspect Evidence and its SourceSpan, and make author decisions.
9. Commit completed draft material as a new source revision, then review new, changed, and invalidated Memory candidates.
10. Accept, edit where allowed, or reject every candidate. Submission creates an auditable ChangeSet and, only when accepted changes exist, a new immutable Memory version.

Primary actions always return to a valid product route. Loading, empty, failure, stale, and recovery states retain the current project and draft selection. A failed analysis or commit does not discard unsaved editor text or already-entered review choices.

## Author workspace shell

The desktop shell keeps Home and Works in a persistent global rail and project tools in a separate project rail. Authors may collapse the global rail to icon width; the preference is stored in that browser and the released space is returned to the project and writing surfaces. On smaller viewports the shell returns to its established responsive navigation instead of applying the desktop collapsed state.

Operational pages use the available wide-screen canvas with bounded readable widths. Project and writing surfaces may grow wider than forms, while create, import, and account-security forms remain centered in the main region. Type sizes follow one page, section, item, body, and metadata hierarchy across routes.

Writing and Checking also offers a desktop immersive manuscript surface. It is an overlay over the existing workspace, not a separate draft: entering, editing, leaving with Escape or the exit control, and returning all use the same in-memory title and body. The author may change body font size, line height, and readable column width, or collapse the auxiliary continuity-issue rail. These display choices remain available while the project view is mounted. Real-time character counts are local calculations and do not establish product records.

Immersive writing keeps the established optimistic draft contract. Only the explicit Save Draft action sends a write with the current base revision and idempotency key; entering, typing, changing display settings, and exiting never autosave. A conflict or other failed save keeps the local text visible and reports the failure beside the save control. Evidence opened from the auxiliary issue rail still uses the existing read-only Evidence and SourceSpan flow.

The author profile follows a fiction-workbench hierarchy: author identity, real writing totals, continue-writing and works access, then secondary profile settings. Project, chapter, word, and status totals are derived from the signed-in account's stored projects, chapters, and current drafts; tutorial projects are excluded. No follower, revenue, rank, ticket, or other platform-business metric is invented. Display name and one of four bundled bitmap avatars may be changed through the existing profile revision contract; avatar choice lives in a compact dialog rather than the main information flow.

## Seven information boundaries

| Layer | Meaning | May establish canon? | Author control |
| --- | --- | --- | --- |
| Author Context | Planned story, character, and world intent | No | Create, edit, reorder, archive |
| Character aliases | Author-confirmed alternate names attached to a written character record | No | Add, edit, archive with optimistic version checks |
| Foreshadow records | Author-maintained future, planted, developing, resolved, or abandoned threads with written-source links | No | Create, edit, archive, and decide whether an AI candidate becomes a record |
| Revision tasks | Persistent author work accepted from bounded Issue-specific suggestions | No | Accept or edit candidates, update progress, return to the draft, explicitly save and recheck |
| Draft and SourceSpan | Saved or committed prose that has been written | No, not by itself | Write, save, inspect, append |
| Story Memory | Author-confirmed facts in an immutable version | Yes | Accept, edit eligible candidates, reject |
| AI analysis | Briefs, alignment results, continuity findings, and Memory candidates | Never automatically | Trigger, cancel, retry, inspect, decide |

Planned material may be cited as a plan source but never as proof of written prose. Written material may support a finding but does not enter Story Memory without an author decision. AI output is never fed back as confirmed canon until the corresponding author-controlled transaction succeeds.

## Eight AI decision points

| Decision point | Bounded input | Output | Author control |
| --- | --- | --- | --- |
| Chapter brief | Current Author Context snapshot, current Memory version, recent SourceSpans, saved draft identity | Summary and sourced preparation items | Generate, cancel, retry, inspect sources |
| Plan alignment | Current Author Context snapshot and saved draft claims | One controlled status per selected story plan with Evidence when present | Generate, cancel, retry, inspect; no prose edit |
| Change impact | Author's explicit proposed change plus bound draft, source, Memory, Author Context, and alias snapshots | Evidence-backed affected chapters, characters, world records, Memory records, and plans | Generate, cancel, retry, inspect; no replacement prose or automatic write |
| Bounded Q&A | One author question, selected confirmed/written/planned scopes, and exact bound versions | Answered, partial, insufficient, or conflicting result with layer-specific Evidence | Generate, cancel, retry, inspect; no product-data write |
| Foreshadow scan | Saved draft, bounded SourceSpans, draft claims, and current author foreshadow snapshot | Evidence-backed AI candidates only | Accept, edit and accept, or reject each candidate; no automatic record creation |
| Revision plan | One to eight open Issues from the same current continuity Run, their sufficient Evidence, and exact project-state bindings | Exactly one bounded action suggestion per selected Issue | Accept, edit and accept, or reject; accepted items create tasks only, never prose or canon |
| Continuity review | Saved draft claims, bounded confirmed Memory, resolvable written sources | Reviewable issues with severity, explanation, Evidence, and optional Memory suggestion | Inspect Evidence; accept, edit, or reject eligible suggestions |
| Memory delta | New source revision, active confirmed Memory, controlled predicates | New, changed, or invalidated fact candidates bound to exact records and Evidence | Accept, edit eligible candidates, reject, then submit |

Requests use deterministic bounded retrieval, strict JSON schemas, explicit model and schema labels, token limits, and resolvable source identifiers. The Provider has no tools, external search, vector database access, whole-novel access, or authority to write product records directly.

## Version and audit graph

| Node | Purpose | Binding rule |
| --- | --- | --- |
| SourceRevision | Immutable committed written corpus | Increases only after a successful SourceChangeSet commit |
| AuthorContextVersion | Immutable snapshot of editable future intent | Increases after each accepted planning mutation |
| AliasVersion | Project binding plus per-character optimistic version for author-confirmed aliases | Increases after each accepted alias add, edit, or archive |
| ForeshadowVersion | Project binding plus per-record optimistic version and immutable author audit | Increases only after an accepted author record create, edit, archive, or candidate acceptance |
| RevisionTaskVersion | Project-wide candidate-decision binding plus immutable per-task status history | Increases only when a candidate creates a task or an existing task changes progress |
| DraftRevision | Saved state of the active draft | Increases after an explicit save |
| MemoryVersion | Immutable author-confirmed canon snapshot | Increases only when accepted Memory changes commit |
| Run | Immutable AI request, state bindings, retrieval metadata, and terminal result | Bound to project, draft, source, Memory, and Author Context versions as applicable |
| Evidence | Resolvable pointer to Author Context, a draft claim, Memory record, or SourceSpan | Must belong to the active project and bound version |
| Decision | Author response to a reviewable item | Cannot be inferred from AI output |
| ChangeSet | Atomic audit of before/after values, Evidence, decisions, and add/replace/retire operations | Commits with the target Memory version or rolls back completely |

Staleness is a state-binding mismatch, not a visual warning only. A changed draft, plan snapshot, source revision, Memory version, alias snapshot, or relevant foreshadow snapshot invalidates any Run that depended on it. Retry creates a new Run over the same valid immutable input; stale lineage must be regenerated from current state.

## Failure, retry, recovery, and rollback

- Invalid JSON, schema mismatch, unsupported predicates, duplicate targets, unresolved Evidence, timeout, cancellation, quota or budget stops, and stale bindings fail closed.
- Non-completed Runs create no partial issues, candidates, revision tasks, decisions, source updates, or Memory updates.
- Cancel marks the Run and discards late Provider results. Retry preserves lineage while creating a new Run.
- A review submission is one SQLite transaction. Any validation or storage failure rolls back the ChangeSet, Memory records, version pointer, and coverage audit together.
- Rejected-only and empty Memory reviews record coverage and decisions without increasing MemoryVersion.
- Refresh and logout/login restore server-backed project, saved draft, Run, and review state. Unsaved browser text is intentionally not treated as durable.
- Cross-project and cross-account identifiers resolve as not found and never reveal another workspace.

## Responsive and accessibility contract

Desktop viewports at 1024 px and above are the authoring surface and may open immersive writing. At 390 px the workspace is explicitly browse-only: the immersive entry, draft editor, save controls, revision-plan and task controls, and other mutation controls are absent, while the reason, current draft, plans, revision suggestions and tasks, results, Evidence, SourceSpans, history, coverage, ChangeSet details, author profile, and real work summaries remain readable. Drawers and dialogs keep keyboard focus, Escape returns focus to the trigger, reduced-motion preferences are respected, and the document must not overflow horizontally.

## Known limits

- v1.3.0 is a local release candidate and has not replaced the online v1.2.0 product.
- Revision plans remain bounded action suggestions rather than replacement prose. Task completion is self-reported workflow progress and requires an explicit save and continuity recheck to validate the manuscript. Bounded Q&A cannot answer beyond the selected project evidence, and foreshadow scanning remains a candidate aid rather than an automatic story planner.
- Mobile is browse-only; immersive writing is limited to desktop viewports at 1024 px and above.
- Provider conclusions can vary. Strict schemas and Evidence resolution reduce unsafe output but do not make the model infallible.
- The retained evaluation sets support only their documented claims and are not a general fiction benchmark.
