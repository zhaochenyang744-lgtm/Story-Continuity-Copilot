# v1.3.0 bounded revision plan and task contract

The revision loop converts selected continuity Issues into author-controlled work without turning AI output into prose, canon, or an Issue decision.

## Author loop

1. Start from one completed, current continuity Run and select one to eight open, undecided Issues with sufficient resolvable Evidence.
2. Generate a `revision_plan` Run. It binds the exact draft, source corpus, Story Memory, Author Context, author foreshadow snapshot, source continuity Run, selected Issue identities, and selected Evidence snapshot.
3. Review exactly one suggestion per selected Issue. Each suggestion contains a bounded title, action instruction, priority, and Evidence belonging to that same Issue.
4. Accept, edit and accept, or reject each suggestion. Accepting creates one persistent revision task; rejecting creates no task.
5. Return to the same draft, edit the prose manually, and explicitly save it.
6. Update task progress independently, then explicitly run continuity review again when the author is ready.

The model receives no tools, external search, whole-project dump, or write authority. Suggestions are action instructions, not replacement prose.

## Persistence and state boundaries

`RevisionTaskVersion` is a project-wide optimistic version for candidate decisions. Each task also has an immutable per-task version history. Candidate decisions and task creation are one SQLite transaction, use idempotency keys, enforce a 200-active-task limit and normalized active-title uniqueness, and roll back together on failure.

A suggestion becomes stale when any bound draft, source, Story Memory, Author Context, foreshadow, source Run, selected Issue, or selected Evidence state changes. Pending stale suggestions cannot be accepted or rejected. A task that was already accepted remains available and can move among `todo`, `in_progress`, and `completed`, even after its source analysis becomes stale.

Task status is author workflow metadata only. Completing a task does not edit or save the draft, decide or resolve an Issue, start a Run, commit a SourceChangeSet, create a MemoryVersion, or mutate Author Context or foreshadow records. Reopening a completed task rechecks the current active-task limit and title uniqueness before any audit or version increment.

## Validation and failure behavior

- Provider output must contain exactly one candidate for every selected Issue and no unselected or duplicate Issue.
- Priority is limited to `high`, `medium`, or `low`; titles and instructions are length-bounded.
- Every candidate must cite one to five resolvable Evidence records from its own Issue.
- Invalid JSON, schema mismatch, missing or cross-Issue Evidence, duplicates, timeout, cancellation, stale bindings, version conflict, and cross-project identifiers fail closed.
- Non-completed Runs store no analysis result or candidate. Cancellation discards a late Provider result. Retry creates a new Run with preserved lineage only while the original bindings remain current.

Desktop exposes selection, candidate decisions, task progress, return-to-draft, and explicit recheck controls below the manuscript workspace. At 390 px the same suggestions, tasks, status, and Evidence remain browseable, while every mutation control is absent.

Verification is covered by `backend/tests/test_v130_revision_plan.py` and `frontend/e2e/v130-revision-plan.spec.ts` using the isolated local provider harness with zero external Provider calls.
