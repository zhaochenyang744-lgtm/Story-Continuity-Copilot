## Issue 读取契约

`GET /api/projects/{project_id}/checks/{run_id}?include=issues,evidence` 对每条新结果返回：

- `review_contract_version: "trustworthy_review_v1"`
- `nature`: `confirmed_conflict | possible_conflict | state_change | insufficient_evidence`
- `reasoning`: 引用为何支持该判断，或判断在哪个证据缺口处停止
- `evidence_chain`: `{ evidence_id, role }[]`，角色为 `prior_state | current_context | missing_link`
- `suggested_revision`: 唯一绑定本次 Run 草稿版本的 `{ before, after }`，或 `null`
- `available_actions`: `edit | apply_suggestion | keep_intentional | false_positive` 的子集

旧行不做语义回填，统一只标记 `review_contract_version: "legacy_v3"`；不根据分类、风险或文案推断 `nature`。

新 Provider 结果必须完整通过 `continuity-issue-v4-trustworthy-review` 校验后，以上字段才会持久化。证据链在数据库中保存真实 Evidence ID，而不是 Provider 的 span ID。读取时再次验证 Evidence 归属、来源 revision、Memory 引用和建议文本唯一位置。

## 作者动作门控

`POST /api/projects/{project_id}/issues/{issue_id}/decision` 继续使用既有决定值。后端同时检查：

- Evidence 非空、状态充分，且每条引用均可解析；否则返回 `issue_decision_unavailable`。
- 对可信契约，决定必须由 `available_actions` 授权；否则返回 `issue_action_unavailable`。
- `accept_and_edit` 仍需唯一的直接后继草稿 revision 和原 Run/Issue 编辑上下文。

证据不足项没有可提交动作，也不阻塞只针对可决定 Issue 创建 Memory change set。

## 教学进度重新开始

新增：`POST /api/onboarding/progress/restart`

```json
{
  "tutorial_version": "1.2.0",
  "project_id": "project-id",
  "base_revision": 4,
  "confirm": true
}
```

该操作只把当前注册账号自己的教学进度重置为第 1 步、清空已完成事件并追加 `v2_tutorial_progress_restarts` 审计。章节、SourceSpan、草稿及全部 revision、Story Memory 及全部版本、作者资料、Run、Issue、Evidence、决定和 change set 均不改动。接口有 CSRF、所有权、版本与幂等校验。旧 `/api/onboarding/reopen` 仅保留兼容，v1.4 前端不再调用。

重新学习到第 4 步时，用户既可以对未处理问题作出新决定，也可以打开一条已有决定、复习证据与原决定后明确点击继续。后者记录独立教学事件 `author_decision_reviewed`，请求必须同时绑定已有决定的 `run_id` 与 `issue_id`；服务端要求证据查看步骤已完成，并核验该决定、Issue、Run 和教学作品属于同一当前账号。该事件只推进教学进度，不插入或更新 `v2_decisions`，旧检查或已过期检查也可作为只读复习对象。没有既有决定、没有完成证据查看、绑定不匹配或跨账号时均返回 `tutorial_decision_review_unavailable`。

## 迁移、备份与回滚

迁移 140 只为 `v2_issues` 添加 nullable 列，并创建进度重启审计表；不会更新旧 Issue 行。

升级前应在服务停止写入后复制 SQLite 数据库及其 `-wal`/`-shm`（若存在）。旧应用代码可忽略新增列继续读取；若必须移除 schema 140，应停止服务并恢复升级前的整套数据库备份，不应在线删除列或仅替换主数据库文件。
