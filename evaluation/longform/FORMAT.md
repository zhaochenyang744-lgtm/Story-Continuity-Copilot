# 长文本评测集格式说明（longform-eval/1）

本文件写给出题的人（或模型）。照着写，写完运行校验器，校验器报 PASS 才算格式合格。校验器只查格式、长度、引文位置和数量，**不判断标注对不对**，标注的正确性靠出题方自查和验收。

可以对照的最小示例：`evaluation/longform/template/`。它只演示字段怎么写，章节太短、题量太少，只能通过 `--structure-only`。

## 1. 三种集合

| 种类 `kind` | 用途 | 谁能看内容 |
|---|---|---|
| `dev` 开发集 | 开发时反复用来调试和测量 | Claude 可以看 |
| `formal` 正式集 | 第 4 阶段只跑一次，决定是否达标 | Claude 不看，只跑校验器 |
| `import` 导入作品 | 约 30 万字的整部旧稿，用来验收导入和整书检查 | Claude 只看校验器输出 |

一套集合放在一个目录里，例如 `evaluation/eval_set_lf1_dev/`、`evaluation/eval_set_lf1_formal/`、`evaluation/eval_set_lf1_import/`。

## 2. 目录结构

```
eval_set_lf1_dev/
  README.md                  # 可选：本套说明（作品列表、数量）；与 labels、works、自查记录一起计入冻结哈希
  labels.json                # 标注（必需）
  works/<作品key>.md          # 每部作品一个完整原文文件（必需）
  authoring/self-review.json # 出题方逐章自查记录（必需，见第 9 节）
  set.sha256                 # 冻结后由校验器生成，不要手写
```

## 3. 作品原文 `works/<key>.md`

- 全部用中文写（校验器会检查汉字占比）。原创或公版均可；公版作品必须在 `source_note` 里写明书名、版本和改动了哪些地方。
- 用一级标题分章，每章一行：`# 第一章 标题`（`第…章` 可用汉字或阿拉伯数字）。文件第一行就必须是章节标题；章节标题在作品内不能重复；正文里不要再出现任何 `#` 标题。
- 章节长度按"字"计（不算空白）：

| 种类 | 每部章节数 | 普通章节 | 被检查的章节（target） |
|---|---|---|---|
| dev / formal | 8–14 章 | 800–3,500 字 | 2,000–3,200 字，至少 15 句 |
| import | 100–150 章，全书 28–36 万字 | 800–4,000 字 | 2,000–3,200 字，至少 15 句 |

- 句子以 。！？ 结尾（后面可以跟 ” 等收尾引号）。被检查的章节必须是真正的多句正文，像正常小说一样有叙述、对话和细节，不能只写考点。
- **正文必须逐章真正写出来，不能用脚本、模板或句型替换拼装。** 每章有自己的情节推进、场景和对话；不同章节、不同作品之间不能反复使用同样的句子或段落（只换人名、物名也不行）。校验器会检查（见第 10 节末尾）：一部作品里重复出现的句子不超过 3%；在别的章节里再次出现的文字（按连续 20 字计）不超过 5%；同一套里的不同作品之间不能有任何一段 20 字以上相同的文字。
- **考点要织进叙述里。** 前文事实和问题句应当出现在正常段落中（叙述、对话、人物行动），不要单独写成一句话的段落。校验器要求：标注的问题句和证据句里，单独成段（整段只有这一句）的比例，不超过全套普通句子单独成段比例加 15 个百分点（至少允许 25%）。网络小说习惯一句一段，按它自己的习惯比较。
- 不要使用以下旧名字：灰港、纸月、零号花园、雾港、白塔（以及产品示例作品"灰港回声"）。不同套集合（开发集、正式集、导入作品）之间不能共用作品，也不能有任何一段 20 字以上相同的文字。

## 4. `labels.json` 顶层

```json
{
  "format": "longform-eval/1",
  "set_id": "lf1-dev",
  "kind": "dev",
  "language": "zh",
  "authoring": {"model": "出题模型名称", "date": "2026-10-xx", "notes": "可选说明"},
  "works": [...],
  "targets": [...],
  "selections": [...],
  "subsets": {}
}
```

字段必须正好是这 9 个，不能多也不能少。

**works**：每部作品一项，字段正好是 `key`、`title`、`file`、`origin`、`source_note`。
- `key`：小写英文、数字、下划线，3–41 个字符，例如 `qingyan_lamps`。
- `file`：必须是 `works/<key>.md`。
- `origin`：`original`（原创）、`public_domain`（公版）、`open_license`（允许改编和转载的开放授权作品，如 CC BY，须按授权署名）或 `private_test`（用户本地测试用的有版权作品）；`source_note`：原创填 `null`，其余必填（作者、书名、版本或出处、授权、改动范围）。
- `private_test` 的整套集合**必须放在仓库外**（例如桌面），校验器发现它在仓库目录里会直接报错；这类集合永远不提交、不公开。

## 5. 被检查的章节 `targets`

每个 target 就是"作者勾选这一章去检查"。检查第 N 章时，系统只能使用第 1 到 N−1 章，所以**所有证据都必须来自更早的章节**。

```json
{
  "id": "lf1d-t01",
  "work": "qingyan_lamps",
  "chapter": "第七章 河岸的夜",
  "smoke": false,
  "items": [ ...问题点... ],
  "traps": [ ...陷阱... ]
}
```

- `id`：小写字母、数字、连字符，3–41 个字符，全套唯一（target、问题点、陷阱、selection 的 id 都不能重复）。
- `chapter`：完整章节标题，不带开头的 `# `。被检查的章节至少是第 3 章（前面至少有 2 章）。
- `items`：这一章里埋的问题点，0–3 个。**0 个就是"干净章节"**，用来测误报。
- `traps`：这一章里看起来可疑、其实不矛盾的句子，可以为 0 个。
- `smoke`：只在开发集里用，标出 3–4 章作为日常快速测试（其中至少有一个矛盾和一个证据不足）。正式集和导入作品一律填 `false`。

## 6. 问题点 `items`

字段正好是：`id`、`class`、`category`、`missing_link`、`issue_quotes`、`evidence`、`designated_regression`、`designated_basis`、`explanation`。

### 6.1 两种问题

| `class` | 含义 | `category` | `missing_link` |
|---|---|---|---|
| `conflict` 矛盾 | 这一章的说法和前文确立的事实对不上 | 8 类之一（下表） | `null` |
| `insufficient_evidence` 证据不足 | 这一章把前文没有确立的事说成了定论，中间缺一环 | `null` | 缺的环节（下表） |

矛盾的 8 类 `category`：

| 值 | 含义 | 例子 |
|---|---|---|
| `attribute` | 人或物的属性 | 前文左撇子，这里写惯用右手 |
| `object_state` | 物件的状态或归属 | 钥匙已交出，这里又从自己口袋里拿出来 |
| `relationship` | 人物关系 | 前文是表兄妹，这里成了亲兄妹 |
| `character_knowledge` | 人物知道什么 | 前文明确不知道密码，这里直接输入 |
| `timeline` | 时间先后 | 前文婚礼在出发之后，这里写在出发之前 |
| `event_status` | 事件是否发生、结果如何 | 前文比赛取消，这里写他赢了那场比赛 |
| `location_action` | 某人某时在哪、做了什么 | 前文那晚在码头值夜，这里写那晚在家吃饭 |
| `world_rule` | 世界规则 | 前文规定任何人不得在夜里开城门，这里写守卫半夜开门而无任何例外说明 |

证据不足缺的环节 `missing_link`：

| 值 | 缺了什么 |
|---|---|
| `handoff` | 交接（东西怎么到他手里的） |
| `authorization` | 授权、委托、批准 |
| `provenance` | 出处、来源 |
| `outcome` | 结果（只写了做，没写成没成） |
| `identity` | 身份（是不是同一个人/物） |
| `causation` | 因果（只写了先后，没写是谁造成的） |
| `witness` | 亲眼所见（只是听说） |
| `measurement` | 测量、核对结果 |
| `subsequent_state` | 后来的状态（只写了当时，没写后来） |
| `other` | 其他，需在 explanation 里说清楚 |

### 6.2 引文规则（最重要）

- `issue_quotes`：从**被检查的章节**原样复制 1–2 段文字，每段 6–150 字、不跨行，最多跨两句。它标出"问题出在哪一句"。系统在这句（或它所在的整句）上报问题才算找到。
- `evidence`：1–3 条，每条 `{"chapter": "更早章节的完整标题", "quote": "原样复制的一段"}`，quote 6–200 字、不跨行。
- **每段引文在所在章节里必须只出现一次**。如果一段话出现多次，就把引文加长到唯一为止。
- 一字不差地复制，包括标点。不要写位置数字，校验器会自己算。
- 同一章里，不同问题点、陷阱不能落在同一句上，每个考点要有自己的句子。

### 6.3 其他字段

- `explanation`：1–300 字，说明为什么是矛盾或缺了哪一环。只给验收看，不给系统看。
- `designated_regression`：指定回归题，必须是 `conflict`，并且要求系统给出"明确矛盾"。非指定题填 `false`，同时 `designated_basis` 填 `null`。
- `designated_basis`：指定回归题必填，二选一：
  - `{"type": "timeless_rule", "anchor": "规则里的关键字"}`：前文有一条永久规则（任何情况都适用），anchor 必须出现在证据引文里；
  - `{"type": "shared_time", "anchor": "共同的明确时间"}`：问题句和证据写的是同一个明确时间（例如"三月初七午时"），anchor 必须同时出现在问题引文和证据引文里。

## 7. 陷阱 `traps`

用来测误报：看起来像问题、其实前文能解释通的句子。字段正好是 `id`、`kind`、`quotes`、`evidence`、`explanation`。`quotes` 与 `issue_quotes` 规则相同，`evidence` 写能说明它不矛盾的前文。

| `kind` | 含义 |
|---|---|
| `state_change` | 状态变了，但变化过程前文写过 |
| `compatible_new_detail` | 新出现的细节，和前文不冲突 |
| `rule_exception` | 规则本身写了例外，这里正好符合例外 |
| `similar_name` | 名字相近的另一个人/物 |
| `time_passed` | 时间过去了，状态合理改变 |
| `reported_belief` | 人物说错了或在撒谎，叙述没有当真 |

## 8. 多章选择 `selections` 与子集 `subsets`

- `selections`：模拟作者一次勾选多章一起检查，用来测多章的时间和费用。每项 `{"id", "work", "chapters": [章节标题, ...]}`，2–8 章、同一部作品、不重复，**每一章都必须是 target**。
- `subsets`：可选的命名子集，`{"名字": [target id, ...]}`，没有就写 `{}`。

## 9. 自查记录 `authoring/self-review.json`

```json
{"targets": [{"target_id": "lf1d-t01", "unintended_issues_checked": true, "notes": "已逐句核对，除标注外无其他矛盾"}]}
```

每个 target 都要有一条，并且 `unintended_issues_checked` 为 `true`，表示出题方已逐句核对过这一章：**除了标注的问题点，没有意外写出别的矛盾或证据不足**。长章节很容易无意中写出矛盾，系统报出这种问题会被算作误报，所以这一步很重要。校验器只查是否每章都有记录，不读 notes。

## 10. 数量要求（校验器会检查）

| 要求 | dev 开发集 | formal 正式集 | import 导入作品 |
|---|---|---|---|
| 作品数 | 3 | 4 | 1 |
| 被检查章节 | 12–18 | 24–32 | 不限 |
| 矛盾 | ≥12，覆盖全部 8 类 | 正好 24，每类 ≥2 | 问题点共 18–22 个，其中矛盾 ≥14、至少 6 类 |
| 证据不足 | ≥8，至少 3 种缺失环节 | 正好 12，至少 4 种缺失环节 | ≥4 |
| 陷阱 | ≥8，至少 4 种 | ≥16，至少 4 种 | ≥8 |
| 干净章节（无问题点） | ≥3 | ≥6 | ≥10 |
| 指定回归题 | ≥1 | 正好 3，两种 basis 都要有 | 不要求 |
| 多章选择 | 至少一个 5 章、一个 8 章 | 正好两个 5 章、一个 8 章，来自至少 2 部作品 | 不要求 |
| smoke | 3–4 章 | 全部 false | 全部 false |
| 证据距离 | ≥40% 的问题点证据在 3 章以前 | 同左 | ≥10 个在 10 章以前，≥3 个在 50 章以前，至少 3 个问题点位于前 20 章内 |

每个被检查章节最多 3 个问题点。

所有种类都要满足的正文要求：一部作品内重复句子 ≤3%；在其他章节再次出现的文字 ≤5%；同一套内不同作品之间没有相同的 20 字片段；标注的问题句、证据句中单独成段的比例 ≤ 全套普通句子单独成段比例 + 15 个百分点（至少允许 25%）。

## 11. 出题要点（来自前几套评测的经验）

1. **想考的事实要在前文写成直白的陈述句**（"钥匙交给了守塔人"），不要只靠暗示，否则系统提取不到这条事实，题就变成了考"读心"。
2. **问题句要和证据共享独特的名词**（人名、物名、地名），让系统能检索到对应的前文。
3. **证据不足题要真的缺一环**（缺交接、授权、出处、结果、身份……），不能写成"只是没写时间的矛盾"——那会被当作可能矛盾。
4. **矛盾不要写得过于露骨**，也不要在问题句旁边加"奇怪的是""居然"之类的提示词。
5. 考点在章节里自然出现，前后有正常的叙述，不要把问题句放在章节开头或结尾的固定位置。
6. 一部作品里的人物、物件、地点要前后一致；除了标注的问题点，其余内容都要经得起逐句核对（见第 9 节）。
7. 证据距离要拉开：一部分证据就在上一两章，更多的要在好几章以前，导入作品里还要有几十章以前的。
8. **不要用程序生成正文。** 评测要模拟真实作者的稿子：用模板拼出来的章节里，同样的句子到处出现，系统检索和筛查会变得异常容易或异常困难，测出来的数字没有意义。可以用程序做核对（数字数、查引文、查重复），但正文本身要逐章写。
9. 出题过程中的脚本、草稿、核对记录等工作文件放在仓库外（例如桌面"长文本任务\工作文件\"），不要放进仓库。

## 12. 校验与冻结

在仓库根目录运行（Windows PowerShell）：

```powershell
.\.venv\Scripts\python.exe -m evaluation.longform.validate evaluation\eval_set_lf1_dev
```

- 报 `PASS` 才算合格；`ERROR` 行会写明是哪个 id、哪个字段、第几章，但不会显示原文。
- 开发集和正式集要互相查重：

```powershell
.\.venv\Scripts\python.exe -m evaluation.longform.validate evaluation\eval_set_lf1_formal --against evaluation\eval_set_lf1_dev --against evaluation\eval_set_lf1_import
```

- 全部合格后冻结（生成 `set.sha256`，冻结后不能再改任何文件）：

```powershell
.\.venv\Scripts\python.exe -m evaluation.longform.validate evaluation\eval_set_lf1_formal --freeze
```

- 冻结后检查：加 `--require-frozen`。哈希对换行符不敏感（Windows 的 CRLF 不影响）。
