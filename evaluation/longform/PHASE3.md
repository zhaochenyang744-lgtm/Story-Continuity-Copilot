# 长文本第 3 阶段：原文段落检索测量记录（2026-10-04）

用 `evaluation/longform/retrieval_eval.py` 离线比较新旧检索，不调用模型、不花钱。新检索在 `backend/app/passages.py`（`passage-v1-bm25-entity`），本阶段尚未接入检查流程（第 4 阶段接入）。

复现（免费，约 1 分钟）：

```
python -m evaluation.longform.retrieval_eval --set evaluation/eval_set_lf1_dev --facts evaluation/results/longform-facts-lf1-dev-p2-new2.json
python -m evaluation.longform.retrieval_eval --set evaluation/eval_set_lf1_import --facts evaluation/results/longform-facts-lf1-import-p2-new.json
```

口径：每个标注点用它所在的句子（或段落）去检索，只能检索被检查章之前的章节；前 k 条结果与标注依据句有重叠即算找到。"全部依据@k"要求一个点的所有依据句都在前 k 条内，"任一依据@10"只要求找到其中一条。事实库用第 2 阶段新版导入真实提取的事实（开发集 151 条，导入作品 1,053 条）。

## 方法

- 旧：现在线上的路径。按共享字对给整章打分取 5 章，引擎再挑 3 章，每章截 500 字窗口。
- 句子：新段落索引，每句一查。
- 句子+事实：在"句子"基础上加事实路线：事实按措辞打分，映射到其所在章最贴合的原文段落，与直接检索结果轮流排入。
- 段落 / 段落+事实：用被检查章的约 500 字段落整段去查。
- 多句合并 / 多句合并+事实：检查一个段落，但逐句检索后按名次合并。

## 观察

1. 新检索全面好于旧检索：开发集 0.35→1.00，导入作品 0.22→0.72（全部依据@10）。开发集已达到预先登记的开发目标（全部依据@10 ≥ 0.90）。导入作品不是门槛集，只作对照。
2. 用单句查最好。整段查或逐句合并会把关键句的词淹没，30 万字作品上尤其明显。所以第 4 阶段应先筛出可疑句，再用可疑句检索，而不是整段检索或对每句都检索。
3. 事实路线主要帮的是"只共享人物和属性类型、不共享用字"的冲突（紫发碧眼 对 赤色眼眸）：导入作品句子查询@3 从 0.33 升到 0.50，段落查询@10 从 0.39 升到 0.67。开发集段落查询@5 略降（0.80→0.70），因为事实结果排在前面挤掉了直接结果，@10 不受影响。
4. 实体加权和属性类别的帮助很小，导入作品上不加实体反而略好。暂时保留，第 4 阶段再看。
5. 导入作品剩下 5 个未全部找到的点：
   - 两个点要求两条依据同时找到，现已找到其中一条（如"紫发碧眼"那题找到了第 4 章，没找到第 11 章那句"赤红的眼瞳"）；
   - 一个是知识型冲突（"只听说过守望寰宇"对第 8、9 章出现的其他组织名），需要两步推理；
   - 两个是称呼不同（"妹妹"对"小曦"，"波旁小姐"对"德莉莎"）。其中"妹妹"那题检索排第一的是第 1 章"红发的小女孩"，同样能证明矛盾，只是标注只列了第 9 章。所以这项数字偏保守。

## 第 4 阶段的取用方式

- 检查一章时先筛可疑句，每个可疑句用"句子+事实"检索前 8–10 段，最多每章 2 段，只查被检查章之前的章节。
- 段落按需切分，不落库；落库与否看第 4 阶段的耗时再定。
