# 长文本第 4 阶段：先筛查再核实（进行中，2026-10-04）

新流程在 `backend/app/review_screening.py` 与 `ContinuityEngine._execute_screened`（`engine.py`）。默认启用，`CONTINUITY_REVIEW_PIPELINE=legacy` 回到逐句审核；每次检查按创建时记录的版本执行。

## 流程

1. **筛查**（不思考，一章一次）：整章句子 + 每句最相关的 Story Memory 事实（最多 90 条），模型标出值得细看的句子，并标"矛盾 / 缺依据 / 值得核对"三类和相关事实。短稿（≤6 句）不筛查，逐句审核，与旧流程一致。
2. **兜底**：句子提到事实库里已有的人或物、又写了具体属性（颜色、年龄、出身、亲属、数量等），即使没被标出也补进来，按"值得核对"处理。
3. **核实**：每句配第 3 阶段的原文段落检索（事实路线优先，约 2,500 字以内、最多 8 段），只查被检查章之前的章节；整章作为上下文。
   - "矛盾 / 缺依据"：直接用思考模式审核，每次最多 2 句。
   - "值得核对"：先过第二道筛查（不思考，每次 8 句，带上每句的原文段落，只给每句打 0–3 分），2 分及以上的按分数从高到低、每章最多 4 句送思考审核。（早先的"快速审核"——不思考地套用完整审核规则——几乎从不升级，已取消。）
4. 一句的格式错误只让这一句"未判定"，不再拖垮整章；没证明同一时间的"确定矛盾"在本地降为"可能矛盾"（审核规则本身就这样规定），不再花一轮思考去返修。

## 测量工具

- `screen_eval.py`：只跑筛查（每章约 1 分钱）。`--app-memory` 用应用自己导入并提取的事实。
- `review_eval.py`：在进程内跑筛查 + 核实，逐次记录 token、思考长度、返修原因，不需要每章重新导入。
- `run.py --live-check`：完整应用流程，导入和建库用回放缓存，检查本身实时调用，用时有效。

## 结论

1. **筛查可靠**：开发集用两种事实库（导入整本的事实、应用按章导入的事实）各测一次，问题句都 100% 被标出，标出文字约占全章两成；30 万字导入作品上也是 100%，约占四成。
2. **不思考的中间一层很难调**：套完整审核规则时几乎全放行，是/否提问时几乎全升级；改成打分加每章上限后，成本可控，矛盾召回可以过线。
3. **思考审核本身的判断不稳定**：同一题在不同轮次时有时无，证据不足题最明显；单次正式运行有较大运气成分。
4. **成本和时间**在门槛附近：平均约 0.30 元、中位约 1 分钟；思考失控（达到输出上限后重答）约占三分之一的费用，也是个别章节 3 分多钟的原因。

## 修过的问题

- 段落编号与 SourceSpan 编号对不上，"永恒规则"依据永远不成立，触发大量昂贵返修。
- 时间锚点检查把"这一时段"当成钟点，又把"十六时……十七时才离开"当成两个时刻。
- 新检索只认汉字，英文稿什么都检索不到（V8 离线用例发现）。
- 筛查给的事实按随机编号排序，同一章每次结果不同，也无法回放复现。
- 短稿误用"每批 2 句"，让短文本的调用次数和额度预检都变了。
- 第二道筛查并行时在工作线程里复制上下文，计费上下文丢失，整章失败。
- 思考审核偶尔返回坏掉的 JSON，旧逻辑让整章失败；现在只让那一句"未判定"。
