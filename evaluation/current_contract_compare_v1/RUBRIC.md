# Current-contract comparison set V1

Status: **seen development candidate for independent gold review**. Four new synthetic works, eight decision axes and 24 close cases: eight confirmed conflicts, eight compatible controls and eight insufficient-evidence candidates. The cases are not a blind holdout and have not been run against a real Provider. V8 challenge patterns informed the design; `v8-lineage.json` excludes all old case inputs and records thematic mappings. The old seal/thread motif was replaced with a pneumatic carrier pressure/cap rule.

Each case stores its exact draft, expected class and category, specific required SourceSpan labels and hashes, time or timeless-rule policy, and a per-axis rationale. `actual-inputs.json` is UTF-8 and captures the full current API business request with a deterministic no-issue stub. `contract-probe-results.json` checks that a minimal proposed decision can pass `ContinuityEngine.validate` on the captured request. `api-score-probe-results-v2.json` independently sends a scripted minimal decision through a fresh isolated API/database and checks the **actual persisted Issue shape**: `status=open`, semantic class in `classification`, no persisted `temporal_basis`, and Evidence included by `include=issues,evidence,metrics`. These probes demonstrate input delivery, contract representability and score plumbing; they do not establish that a model will reach the expected decision.

## Scoring

Use `score.py` on full product run views with included issues and evidence. A terminal failure is a separate `terminal_failure`, never a no-conflict pass. For no conflict, require zero issues. For insufficient evidence, require one target-claim Issue with `classification=insufficient_evidence`, `nature=insufficient_evidence`, only insufficient Evidence, and the declared unknown SourceSpan set. For confirmed conflict, require one target-claim Issue with `classification=conflict`, `nature=confirmed_conflict`, correct category, and every declared direct SourceSpan as sufficient/contradicts. The score checks claim text and never relies on lifecycle `status` for semantic class. Cases with unavailable issues are unscorable, not failed or passed.

The raw model output must be reviewed separately for temporal_basis, argument quality, omissions and any bounded repair. The final API deliberately does not persist temporal_basis. A completed `confirmed_conflict` has passed the current engine's temporal qualification, but the final API alone cannot reveal which raw anchor or rule relation the model supplied. Do not invent that field in a product record. For a future real run, save raw parsed answers and normalization metadata, compare them with the full captured business request, and score final product independently. No aggregate accuracy claim is authorized by these offline probes.

The `insufficient_evidence` cases are phrased as claims about what *existing records establish*, not merely new later events. Four require two SourceSpans to expose the unresolved link. In the timeline and location triples, a later compatible action is a no-conflict control. The knowledge triple also has a legitimate later learning control. The relationship control frames a kinship falsehood as an explicit lie; the attribute control frames an earlier color as a recollection. Independent semantic review must still adjudicate whether each record-based missing link is an issue under the product contract before any formal quality run.

## Boundaries

Only offline scripted providers were used here. No real comparison-set Provider calls, no production seed, no author data, no release Gate. The V8 historical failure remains a separate result. Passing 24/24 input, contract and API score probes is not a model score or independent acceptance of gold labels.
